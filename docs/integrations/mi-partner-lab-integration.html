Vyara ⇄ MI Partner Lab Integration

How the Vyara clinic system books lab tests on the Mahajan Imaging (MI Partner) Salesforce platform using only the endpoints that already exist — no development required on the lab side. Vyara sources the slot and books; the lab collects the sample and posts status back.

DRAFT v1 · for review Date 2026-08-21 Owner Vyara Engineering Audience MI Partner / Salesforce team
At a glance

Vyara books; the lab builds nothing

The guiding constraint: no new development on the Salesforce side. Vyara uses the partner’s existing getAvailableSlots to source a slot and their existing bookFullAppointment / EnquiryCenterAppointment to book it. The lab’s only involvement is collecting the sample and posting the status webhooks it already sends.

Zero lab dev

Only existing endpoints. Every call Vyara makes already exists in the partner’s UAT collection. Nothing new to build, no schema change requested.

Who books the slot

Vyara — two ways. Reception books at prescription time (option 1), or the patient books from their portal (option 2). Both call the lab’s existing booking endpoints.

How Vyara stays in sync

Three webhooks back to Vyara. The lab posts appointment status, report availability, and centre-collection outcomes — the same webhooks it already sends.

Responsibilities

Who does what

Vyara owns the booking so the lab has nothing new to build. The lab’s role is unchanged from how it already serves partner bookings.

VYARA Clinic system

  • Registers the patient; doctor prescribes tests; on sign, generates a unique orderNumber.
  • Sources a slot from the lab’s existing getAvailableSlots (reception or the patient chooses).
  • Books via the lab’s existing bookFullAppointment (home) / EnquiryCenterAppointment (centre).
  • Exposes three inbound webhooks and reconciles status back onto the order.
  • Syncs the lab’s test and centre masters to map our tests to theirs.

MI PARTNER Salesforce / lab

  • Builds nothing new — serves the existing slot + booking endpoints as-is.
  • Receives the booking and creates the work order / case (existing behaviour).
  • Home collection: dispatches a phlebotomist to the patient address.
  • Centre collection: hosts the patient at the named centre.
  • Runs the tests and posts appointment status + reports back to Vyara.
End-to-end flow

The order, start to finish

Solid arrows are calls Vyara makes to the lab; dashed arrows are webhooks the lab posts back to Vyara. No appointment time crosses from Vyara — that is set by the lab.

Vyara MI Partner / Salesforce → solid = Vyara calls the lab’s existing endpoint ⇠ dashed = lab response / webhook to Vyara
  1. Vyara · Sign & create order

    Doctor signs the consultation. Vyara materialises the selected tests, generates a unique orderNumber, and creates the order awaiting a slot. No lab call yet.

  2. Vyara → Lab · Find slots (existing)

    Reception (option 1) or the patient in their portal (option 2) fetches bookable slots from the lab’s existing getAvailableSlots — pincode + preferred time.

  3. Vyara → Lab · Book (existing)

    Vyara books the chosen slot via the lab’s existing bookFullAppointment (home) or EnquiryCenterAppointment (centre). The order moves to SCHEDULED on the ack.

  4. Lab · Collect the sample

    Home: the lab’s phlebotomist visits the address. Centre: patient attends the named centre. Unchanged lab behaviour.

  5. Lab → Vyara · Status webhooks

    The lab posts appointment status, the report pointer + lab number, and any centre outcome — the webhooks it already sends. Vyara reconciles them onto the order.

Collection modes

Home vs centre

HOME Phlebotomist visit

Vyara books via bookFullAppointment with the patient address and the chosen slot. The lab dispatches a phlebotomist. Collection routing and capacity stay in Salesforce.

CENTER Walk-in at a centre

Vyara books via EnquiryCenterAppointment with the CentreID (from getAllCenters) and the chosen slot. Centre outcomes come back on the dedicated center-status webhook.

API · Inbound

Webhooks the lab calls on Vyara

Vyara exposes these three endpoints. The lab (Salesforce) posts to them as events occur. Base URL is Vyara’s app host — the full base is shared privately, of the form https://<vyara-host>/api/webhooks/lab.

Auth (interim). Every request must carry the shared secret in the x-lab-webhook-secret header. Missing/incorrect → 401. We’re open to switching to bearer, HMAC signature, or IP allow-listing — see open items. Vyara acks fast: 200 even when no matching order is found (matched:false), so the lab isn’t pushed into a retry storm; 400 only for a malformed payload.

API · Outbound

Calls Vyara makes to the lab

All calls target the MI Partner apexrest base and are authenticated with an OAuth2 client-credentials bearer token, cached and refreshed by Vyara. Every endpoint below already exists in the partner’s UAT collection — nothing new is requested.

No development required from the lab. Vyara sources a slot from the existing getAvailableSlots and books via the existing bookFullAppointment / EnquiryCenterAppointment. Please confirm we may use these endpoints for this flow, and confirm the getAvailableSlots response shape (see open items).
POST /services/oauth2/token Vyara → Lab

Standard Salesforce client-credentials flow. Vyara caches the token and retries once on a 401 with a fresh token.

Request (form-encoded)
grant_type=client_credentials&client_id=<id>&client_secret=<secret>
Security. The UAT Postman collection ships client_id/client_secret in the token URL query string. Please rotate those and share fresh credentials over a secure channel — Vyara stores them as server-side secrets only.
POST /services/apexrest/getAvailableSlots Vyara → Lab

Existing endpoint. Vyara fetches bookable slots so reception or the patient can choose one. The chosen slot’s serviceTerritoryId / serviceMemberId + start/end are carried into the booking call.

Request
{ "pincode": "110030", "preferredDateTime": "2026-08-25 10:00:00" }
Please confirm the response shape. Vyara reads a list of slots (start/end + service ids) from the response. Our client parses common shapes defensively and offers a manual-time fallback, but a confirmed schema lets us drop the fallback.

GET /services/apexrest/getAllProducts Vyara → Lab

Test master. Vyara caches this and maps our catalogue tests to the lab’s testId / testName so the booking carries the correct ids.

GET /services/apexrest/getAllCenters Vyara → Lab

Centre master. Vyara caches this to resolve the CentreID used in CENTER-mode bookings.
